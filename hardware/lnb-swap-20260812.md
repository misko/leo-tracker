# LNB replacement, 2026-08-12 — lnb-c and lnb-d

Both LNBs on radio `pluto-19f2` were replaced at roughly 21:44 local
(2026-08-13 04:44 UTC).  The two new units are identical to each other.
`pluto-5d4d` (lnb-a, lnb-b) was not touched.

Captures ran continuously across the swap — there is no gap in the timeline to
find it by.  The boundary is bracketed in `epochs.json`; the capture starting
`20260813T044218Z` may straddle the disconnection and should be excluded from
either side.

## Why this file exists

`lnb-calibration.json` keeps **no history**.  Each daily run of
`leo-tracker-lnb-calibration.timer` rewrites it wholesale, so the file only ever
describes the most recent measurement.  The pre-swap snapshot was copied out
before the next run could overwrite it (see `backups` in `epochs.json`).

Receiver labels are reused across hardware changes.  The 18,330 reports and 337
corpus entries either side of this swap all say `lnb-c` and `lnb-d`.  Nothing in
the data distinguishes the old units from the new ones — only the timestamps in
`epochs.json` do.  Any statistic that pools across this boundary is pooling two
different receivers.

## What the old hardware was

| | lnb-c | lnb-d |
|---|---|---|
| absolute LO offset | +430.7 kHz (n=13, SE 12.6) | +20.0 kHz (n=61, SE 5.8) |
| survey active fraction (23.5 h, 2808 tunings each) | **6.5%** | 21.2% |
| calibrated mismatch (c − d) | +434 408 Hz | — |

The absolute offsets come from a Doppler-symmetry sweep over recorded corpus
probes: Doppler is symmetric (49.998% approaching over 63M satellite-instants),
so `E[Doppler] = 0` and the mean measured offset converges on the receiver's own
error.  Its falsification test is that `lnb-c − lnb-d` must reproduce the
independently calibrated +436 kHz; over 240 probes it gives +410.7 kHz (1.8σ),
and `lnb-a − lnb-b` gives +9.5 kHz against a calibrated −4.4 kHz (1.5σ).  The
refinement residuals sit at +5.1, −9.8, −4.0 and +12.4 kHz, well inside the
±58.3 kHz half-spacing of the bank, so the fine stage is correcting rather than
wandering.

### lnb-c's deficit was not its LO offset

The pre-dwell survey spans ±700 kHz centred on zero and does not consult
`receiver_centers`, so a port at +430 kHz still sits within 58 kHz of a bank
hypothesis and loses only about 10% of score.  That cannot produce a 3.3×
detection deficit.  The old lnb-c had a hardware fault beyond its oscillator —
which is what replacing it was meant to clear up, and predicts the two ports
should now track each other closely.

## Consequences of the swap

The stored calibration describes hardware that no longer exists.  Until it is
cleared or re-measured, `receiver_centers("pluto-19f2")` returns
`(+434 408, 0)`, so the dwell analysis searches:

| receiver | window (±300 kHz) |
|---|---|
| lnb-c (rx0) | +134 to +734 kHz |
| lnb-d (rx1) | −300 to +300 kHz |

A new LNB anywhere near zero falls outside lnb-c's window entirely.  A missing
entry falls back to `(0, 0)`, which is the safer default.

Note that deleting the entry also suppresses the automatic alert: the
`ports_exchanged` / `shift_hz` check in `lnb_calibration.py` skips any radio
whose previous entry is absent, so the swap will not be flagged in the next
run's `alerts` array.  This file is the record instead.

Re-measuring is better than either.  `receiver_centers` prefers a
`measured_centers_hz` field (absolute, per receiver) over the difference, and
the sweep above produces exactly that.  Once ~40 post-swap corpus probes exist,
measure both new units directly rather than waiting for the difference-based
calibration to converge across a contaminated 900-report window.
